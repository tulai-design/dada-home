# A3 深度主题与创意工坊架构设计

## 目标

用户要求重点推进架构评估 A3：审查当前代码结构，让后续开发深度定制主题和由 Agent 修改主题更容易，同时为未来创意工坊热插拔主题、插件保留清晰演进路径。

初始研究先形成基于代码的架构审查、方案比较与纵向实施计划；随后按用户确认依次实施四个子项。父任务承载本地 A3 交付，在线工坊分发服务与第三方执行权限保留为后续范围。

## 已知约束

- 基线 `27358e2`，分支 main，初始工作区干净；A1/A2 已完成。
- 保留主题外观、页面与应用数据的现有分离，以及 App/Applet 沙盒和 Web/扩展双平台能力。
- 不要求旧存储兼容或迁移桥；不自动清空本地数据或操作真实远端。
- 主题在当前产品术语中指外观，实际内置主题还承载桌面交互；必须明确视觉数据与可执行外壳的职责。
- 唯一任务系统是 Trellis，不覆盖已有掌机主题与存储任务。
- 用户已于2026-10-30确认分层开放：声明式主题由人和Agent定制，带执行逻辑的代码扩展单独授权并隔离运行。全新可信外壳可随宿主构建，下载任意同源React不是默认热插拔方案。

## 审查需求

- R1：定位主题数据、CSS、导航/窗口/设置、AI 工具与技能的耦合，给出精确源码证据与新增主题的改动面。
- R2：用现有普通外壳、Switch、Win98 验证接口，提出维护者与 Agent 均可操作、可校验的定制模型。
- R3：比较数据主题、受控布局组合与任意代码扩展，明确哪些可运行时热切换、哪些需要可信宿主代码及能力隔离。
- R4：给出预览/应用/撤销/失败恢复、身份与依赖、资源与版本、应用生命周期和扩展平台的必要合同。
- R5：按用户可观察结果拆分演进阶段、验收矩阵与后续任务；区分本轮设计、第一阶段实现和未来创意工坊。

## 初始研究验收

- 每个主要建议能追溯到真实代码/测试，不以通用插件模板代替本项目设计。
- 推荐接口写明职责、调用方需要知道的约束、生命周期、失败模式和状态归属。
- 有可比较方案及取舍、最小垂直交付、可执行后续计划和关键未决产品选择。
- 研究与设计标记为提案，不更新运行时规范为已实现。

## 交付阶段与范围

1. `theme-identity`：派生现有深度主题保留造型/外壳及完整值，修复模板精确身份往返。
2. `shell-host`：普通/Switch/Win98统一宿主Interface与稳定内容舞台，新增外壳集中接入。
3. `theme-authoring`：目录驱动Agent与设置，提供隔离草稿预览和一次应用。
4. `local-theme-packages`：本地声明式包安装/停用/卸载、缺包保留与更新恢复。

子任务有独立PRD和依赖。第一阶段不等于完整A3，父任务只在必要子项和集成验收完成后归档。

## 范围外与延后决策

初始研究轮未修改产品，后续生产重构由上述四子项承载。不建设在线工坊账户、审核、交易和更新服务，不开放任意同源JS，不做新多窗口任务系统或通用插件SDK。第三方代码runner、包二进制全量同步等在对应阶段开始前细化；这不阻塞主题身份与内置外壳设计。

分层开放方向已决，无阻塞本轮架构提案的产品问题。各阶段具体设计、实现与验收分别记录在子任务，已实现行为晋升长期契约；在线工坊与执行代码仍不宣称交付。
