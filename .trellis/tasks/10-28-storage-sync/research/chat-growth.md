# 聊天历史增长、上下文与存储边界审查

日期：2026-10-28。范围：`src/lib/chat.ts`、聊天发起与渲染、工具结果、备份导出，以及聊天进入同步的边界。

本报告仅依据仓库源码。没有读取真实 IndexedDB、localStorage、聊天内容或同步配置；没有启动浏览器、执行外部同步或改变产品代码。下面的容量数字是纯合成数据假设，不是用户当前用量、浏览器真实占用或性能实测。

## 结论

1. **普通启动并不全量加载所有聊天正文，但会全量加载所有对话标题，以及当前对话的所有轮次。** 切换对话同样一次读取该对话的全部轮次；界面最近 40 轮的展示只是内存数组切片，尚无数据库游标分页。
2. **长期历史与发送给模型的上下文已经分开。** 下一次提问默认携带最近 24 轮、累计约 36,000 个 JavaScript 字符的问答及文章资料；不带历史思考与历史工具细节。这个筛选不删除本地历史，也不是完整请求的硬预算。
3. **一轮长期保留全部输入、回答、思考和工具结果文本。** 不保存独立的工具参数字段，也没有聊天附件或图片上传字段；但工具返回的源码、配置、内嵌 data URL，以及用户输入/模型回答中的任意长字符串仍会原样进入聊天。
4. **存储增长的主要候选热点是完整工具结果的重复副本。** `list_applications` 默认返回所有应用的源码，`use_skill` 返回完整技能，`get_workspace` 返回组件配置；通用工具执行和聊天保存层均没有裁剪、去重或外置正文。折叠工具和思考面板只减少 DOM 展示。
5. **本地写入按轮增量，但整轮重写；同步和导出会读取全部历史。** 400ms 合并写入避免每个流式片段都写库；每次落库仍覆盖整轮累计内容。同步会扫描所有聊天记录计算哈希，存在变更时上传合并后的完整同步文档。因此减少模型历史轮数不能解决同步文件增长。
6. **现有清理能力是用户确认后删除整个对话，以及恢复默认时清空全部数据；没有归档、按大小管理、分批导出或自动保留策略。** 建议首先修复保存/导出可靠性并建立无内容暴露的容量可见性，再做真实分页与可恢复归档。自动删旧历史、只留工具摘要、裁剪思考均需要明确产品决策，不能作为透明优化直接实施。

## 2. 一轮长期保存的内容

持久化结构见 `src/lib/chat.ts:15-52`，实际组装见 `src/App.tsx:341-344`、`377-419`。

| 内容 | 是否长期保存 | 是否进入下一轮模型历史 |
| --- | --- | --- |
| 用户 `prompt` | 完整保存；聊天输入框未设置字符上限 | 是，落入上下文筛选的轮次 |
| 模型 `answer` | 流式累加完整保存；工具循环中各次正文均累加到同一轮 | 是，落入上下文筛选的轮次 |
| 模型 `reasoning` | 流式累加完整保存 | 否 |
| 工具结果 | 每次保存 `name/title/ok/text`；结果文本完整保存 | 否；但当前尚未结束的 agent 工具循环会继续携带它 |
| 工具参数 | `ToolStep` 没有 args 字段；正常新建路径不直接长期保存原始参数 | 当轮 wire 消息里保留 tool calls；下一轮重新构造历史时不带 |
| 参考文章 | `title/link/context` 保存到本轮，`context` 含正文纯文本、来源、说明 | 是，`turnContent` 会附回用户消息 |
| 错误、开始/结束时间、中止标记、确认请求 | 保存；确认完成/中止后清除 `pending` | 否 |
| 附件、图片二进制 | 没有专用 attachment/Blob/File 字段，也没有聊天上传入口 | 没有专用多模态消息类型 |
| 字符串中内嵌的图片 URL / data URL | 若已经进入 prompt、answer、工具结果或应用配置，会随字符串完整保留 | 取决于所在字段；问答会进入历史，工具结果只进入当轮 |

聊天输入入口是纯文本 `Composer`（`src/components/Composer.tsx:18-38`、`49-67`）；`ChatMessage` 的 user content 也是字符串（`src/lib/ai.ts:19-23`）。因此目前不宜把“附件图片自动保存”当成已存在的直接增长路径。

但 `list_applications` 将应用 `instance.config` 包括源码一并 JSON 序列化；如果源码中内嵌图片 data URL，它会被当成普通工具结果字符串复制。`get_workspace` 也通过 `describeComponent` 序列化组件完整 config。相关证据：`src/lib/tools.ts:118-119`、`181-186`、`1326-1340`。这条间接路径应在未来尺寸统计中单列“工具正文”，而不是假设都是普通短操作描述。

文章通过 `articleText` 调用 `plainText(..., 10_000)`，超长文本截为 10,000 字符并加省略号；另外还有标题、链接与提示文本，所以保存的整个 `article.context` 并非严格不超过 10,000 字符。证据：`src/lib/articleContext.ts:5-9`、`20-29`；`src/lib/rss.ts:99-106`。原始 HTML 图片标记不会作为这条文章正文路径保存。

当前读库和备份导入并未把每一轮重新投影成严格字段白名单：历史导入只检查 ID，`load` 基本原样返回。因此上述“不保存参数/附件”是正常生产路径的结构事实，不是对任意旧备份或外来未知字段的净化保证（`src/lib/storage.ts:55-64`、`src/lib/chat.ts:107-114`）。

## 3. 上下文窗口与长期历史的区别

`contextTurns` 从最新一轮向前选取，默认最多 24 轮；按 `turnContent(turn).length + turn.answer.length` 累计 36,000 字符（`src/lib/chat.ts:250-266`）。设置页可把轮数改成 1–100（`src/components/AiSettings.tsx:242-244`）。

构建下一次请求时只展开为 user + assistant 正文，不带 reasoning、tools 或 error（`src/App.tsx:350-355`）。参考文章通过 `turnContent` 附回 user 消息；从首页/阅读器新开对话的 `fresh` 分支不带旧历史（`src/App.tsx:328-343`、`351`）。

这个机制已经实现了“长期保存，但只带最近一段到模型”的基本分离，有四个需要在产品表述和后续验收中明确的边界：

- **不是 token 预算。** JavaScript 字符数不能等同于模型 token；也未按实际模型窗口动态计算。
- **至少保留最新一轮。** 长度判断仅在已经选中一轮后生效，所以一个很大的最新历史轮可以单独超过 36,000 字符（`src/lib/chat.ts:262-264`）。
- **不包含本次新问题、系统提示、工具 schema。** 它们在筛选后加入实际请求（`src/App.tsx:383`；`src/lib/ai.ts:226-231`）。
- **不限制当前 agent 循环持续积累的工具内容。** 每轮模型输出的 tool calls 和工具结果都会追加到临时 `messages`；默认最多 14 个模型循环，可配置到 40，每个循环又可能包含多个工具调用。工具数量不是严格限 14 次（`src/lib/ai.ts:85`、`227-252`）。

因此，“缩短带上的历史”可以控制下一次提问的历史部分，但既不减小长期聊天库，也不能保证当轮高密度工具调用不超模型窗口。未来可以独立增加上下文预算/显式压缩机制，保持长期原文和可恢复档案不变。

## 4. 写入频率、重复和增长热点

### 本地写入

流式 answer/reasoning 每个回调都会更新当前轮次；`setTurns` 遍历当前对话全部轮次判断引用变化并标脏，`schedule` 在首个更新后约 400ms 调用一次 flush。时间窗口内的更多更新合并到同一写入；持续流式时大致可达到每秒 2.5 次，实际取决于回调间隔、事件循环和数据库耗时。证据：`src/App.tsx:359-361`、`386-400`；`src/lib/chat.ts:83`、`154-203`。

每次 `flush` 只写脏轮次，不会重新写全部聊天，但写的是该轮**当前完整对象**，包含此前已经得到的所有工具结果、文章资料和累计思考/正文。`put` 覆盖同一 ID，最终数据库没有“每个 token 一条历史”，但数据库写入工作量会高于最终记录大小。对话 metadata 也随每次 flush 更新、排序。切换、新建、删除、页面隐藏/离开及同步开始时另有 flush（`src/lib/chat.ts:181-183`、`205-225`；`src/lib/sync.ts:420`）。结束生成仅修改 `endedAt` 并继续走合并调度，没有明确立即 await 最终落盘（`src/App.tsx:407-419`）。

### 结果体积

| 热点 | 当前边界 | 结果 |
| --- | --- | --- |
| `list_applications` | 默认 `includeSource: true`，未指定 ref 时返回所有应用 | 应用越多、源码越长，每次检查就越大；同一源码在不同轮次重复出现。`src/lib/tools.ts:1326-1340` |
| `get_workspace` | 每个组件含完整 config、页面配置/图层/特效摘要 | 可能复制源码或较长配置；多次查询重复保存。`src/lib/tools.ts:118-119`、`166-186` |
| `use_skill` | 返回整份 `skill.body` | 固定规范和积木目录可能反复复制进聊天。`src/lib/siteTools.ts:623-635` |
| reasoning / answer / prompt | 聊天保存层无统一长度或保留期限制 | 长思考、长生成代码、粘贴文本长期积累。`src/lib/chat.ts:30-52`；`src/App.tsx:377-400` |
| 参考文章 | 正文约 10,000 字符，附标题/来源/链接 | 同篇文章在不同新对话提问时各自有一份上下文。`src/lib/articleContext.ts:5-29` |
| 部分取数工具 | 各自限制，而非全局机制 | `read_article` 约 4,000 字符；`read_feeds` 最多40条、摘要100字符；`web_fetch` 正文500–12,000字符。`src/lib/siteTools.ts:187-206`；`src/lib/searchTools.ts:139-141` |

通用层 `runTool` 仅 `String(await tool.execute(...))`，`dispatchTool` 直接把结果作为 `text` 返回，再持久化到 turn；没有全局截断（`src/lib/tools.ts:1919-1920`；`src/lib/ai.ts:313-316`；`src/App.tsx:394-400`）。`ToolRow` 成功默认折叠，展开后显示整个 text；ThinkingPanel 同样只是条件渲染，均不改变持久记录（`src/components/ToolRow.tsx:11-30`；`src/components/ThinkingPanel.tsx:24-44`）。

### 纯合成量级示例

使用 Python 仅在内存构造英文 ASCII 占位字符，并计算紧凑 UTF-8 JSON 字节；没有打开任何用户数据。

| 假设 | prompt | answer | reasoning | tools.text | article.context | 单轮 JSON | 10,000轮 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| 普通文本假设 | 500 | 2,000 | 1,000 | 2 × 1,000 | 0 | 5,747 B | 54.81 MiB |
| 工具密集假设 | 1,000 | 4,000 | 8,000 | 8 × 20,000 | 10,000 | 183,691 B | 1,751.81 MiB |

这是为了说明重复工具正文能够改变增长量级；这些轮数与文本长度均为假设，不能据此推断用户的实际数量。非 ASCII 文本、转义字符、格式化备份、IndexedDB 实现和索引都会影响实际字节/内存。

另一个只用于理解写入放大的假设：一轮持续 60 秒、每 400ms 都有一次 flush、整轮从接近 0 线性长到 200KiB，则约150次整行快照合计约14.65MiB逻辑内容交给写入层，最终数据库仅保留约200KiB该轮内容。它不是磁盘实际写入量测量，已提前产生的长工具结果还会改变增长曲线。

### 同步和导出放大

同步按记录合并，但并未按网络记录增量传输。每次收集对全部聊天 `getAll`、逐记录 JSON 字符串化/哈希；有本地变化时把整个合并后的 `recs` 文档重新 JSON 序列化上传（`src/lib/sync.ts:199-226`、`423-438`、`490-495`）。加密会再进行 UTF-8编码、AES-GCM、base64封装（`src/lib/sync.ts:266-271`）。这会让长期历史的字节数同时成为 CPU、内存和网络成本。

备份同样先全量读入对象，再形成格式化 JSON字符串和 Blob，缺少游标流式/分包导出（`src/components/SettingsPage.tsx:56-68`）。大量聊天还会增大恢复时一次解析和写入的工作量（`src/lib/storage.ts:34-48`、`55-64`）。详细远端协议与冲突问题由同步专项报告继续讨论。

## 5. 已有管理能力和可靠性缺口

| 能力 | 当前状态 |
| --- | --- |
| 新建/切换对话 | 已有；不删除旧记录。`src/lib/chat.ts:205-220` |
| 删除单个对话 | 已有；弹窗确认后删除该对话全部 turns 和 metadata，无回收站。`src/components/Assistant.tsx:244-255`；`src/lib/chat.ts:222-236` |
| 删除单轮、按日期/大小批量清理 | 未见入口/实现 |
| 归档/取消归档 | 未实现；Conv 没有归档字段。新建对话不等于归档 |
| 搜索历史 | 标题列表已有，未见内容搜索入口 |
| 对话导出 | 没有单对话/选择范围导出；只有整个应用的完整 JSON备份 |
| 导入 | 整体替换、确认后重新加载；不支持选择聊天或合并导入。`src/components/SettingsPage.tsx:353-375`；`src/lib/storage.ts:51-69` |
| 清空所有聊天 | `clearChat` 内部存在；恢复默认和导入替换会调用。恢复默认还清理其他全部数据。`src/lib/storage.ts:15-22`、`55-64` |
| 逻辑字节统计/配额提示/保留策略 | 聊天与数据设置路径未见相应机制 |

两项应先于“规模优化”的可靠性问题，均为静态代码推断，尚未通过故障注入复现：

1. **导出没有主动等待聊天待写队列。** `exportChat` 直接读取数据库，`exportIdb` 和设置页也没有先调用 chat flush；可能遗漏最近400ms内尚未落库的进度/结束状态。同步已有 `await flushChat()`，可以作为边界一致性的参考（`src/lib/chat.ts:270-271`；`src/lib/storage.ts:26-28`；`src/lib/sync.ts:420`）。
2. **聊天写入失败缺少显式错误状态和重试保证。** `db.run` 捕获失败后回落为传入值，write操作的fallback是 `undefined`；chat flush先清空 dirty，再 await写入。因此配额不足、数据库打开失败或事务异常可被上层当作完成，且不会保留 dirty重试。`db.ts` 注释提及 localStorage回落，但聊天路径没有像 componentData那样实现此回落（`src/lib/db.ts:61-76`、`84-93`；`src/lib/chat.ts:155-173`）。容量增长使这项缺口更值得优先解决，不能靠自动删旧聊天掩盖。

## 6. 最小可验收分期建议

以下是供主任务选择的方案，不表示本轮已获实施授权；本报告没有执行迁移、清理或同步行为。

### 第一期：先确保保存和备份可信，明确规模

范围：让 chat存储写入返回明确成功/失败；失败保留待写数据，界面提供状态与可重试路径；导出等待已提交的聊天更新，并明确生成中的导出快照语义；增加按对话/字段的逻辑字节和轮数统计。统计与运行日志仅记录数量、字节和耗时，不记录正文。

最低验收：

- 用隔离的合成仓库注入打开失败、事务失败和配额错误；不得显示保存成功，不得丢失待写队列，重试后可读回相同原文。
- 发送结束立即导出的合成备份包含最后answer/reasoning/tool结果与endedAt；正在生成时导出有定义明确的一致快照。
- 每项体积显示明确区分“逻辑JSON字节”与“浏览器存储估算”，不把后者伪装为精确聊天用量。
- 旧备份导入/导出仍保持兼容；没有新增静默删除、裁剪或自动上传行为。

### 第二期：让打开聊天的成本受限，不减少历史

范围：为 turns提供基于convId+时间/ID的稳定游标分页；初始只读取最新一页，点击更早再读取前页；模型上下文查询与UI已加载页独立；标题列表按需分页或虚拟渲染。若增加索引需要真实数据库版本升级和旧数据迁移验证。

最低验收：

- 合成包含10,000轮的单对话，打开时只读取约定页大小，不对整个对话getAll；加载更早无重复、无遗漏、顺序稳定。
- 在UI只加载部分历史的情况下，模型历史仍遵循独立轮数/字符筛选，不能因用户滚动到哪一页改变请求内容。
- 流式更新只影响活动轮，已加载旧页保持稳定；刷新/切换仍可逐页访问所有历史。
- 删除、备份和恢复覆盖完整对话，不因内存只有一页而漏数据。

### 第三期：提供可恢复归档和范围控制

范围：增加显式归档/取消归档、单对话或选定范围导出及明确的永久删除入口。默认归档保留原文、正文展开和导出能力，只改变活跃列表与读取方式。

最低验收：

- 归档可逆，取消归档后原文、工具详情、文章资料、顺序完整一致。
- 选择导出包含预览数量与范围；导入能说明与已有对话冲突的处理方式。
- 若支持“不把归档上传”，必须新增明确同步协议/范围语义；不能把未参与收集的记录当作删除。现有同步以本地缺失产生墓碑（`src/lib/sync.ts:435-436`），直接过滤会误传播删除。
- 永久删除仍需明确用户操作并告知范围；归档、改显示页数或上下文压缩不触发删除。

### 第四期：依据规模选择同步与重复正文优化

范围：把“本地变更发现”和“远端传输”改为可验证的记录/分片增量机制；必要时将重复的大工具正文放入有版本、内容哈希和引用的独立记录，turn保留引用、摘要与原文可读取性。共享技能正文只有携带历史版本才能替代当时原文，不能简单指向会变化的当前技能。

最低验收：

- 新增一轮只产生该轮和关联metadata等有界变更；网络字节不随全部旧turns线性重传。
- 去重前后能还原相同历史工具原文；引用迁移、删除引用、备份打包和旧备份兼容都有覆盖。
- 合成双设备离线、新建、归档、恢复、删除和冲突场景不会无意丢失旧对话或复活已确认删除记录。

暂不纳入默认方案：只保留最近N天/轮、删除成功工具结果、自动裁掉reasoning、把旧聊天摘要后抹掉原文。这些都会改变用户历史资料，必须单独确定产品契约。上下文摘要可以作为临时请求层功能另行设计，不必伴随长期原文删除。
