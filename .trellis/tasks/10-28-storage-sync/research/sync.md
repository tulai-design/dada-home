# 现有同步审查与存储迁移建议

- 核对日期：2026-10-28。
- 范围：`src/lib/sync.ts`、`src/components/SyncSettings.tsx`、聊天/组件/App/Applet 持久化交界和现有测试入口。
- 本文记录**现状观测和待实现建议**，不表示已完成修复或通过产品验收。
- 只读取仓库源码；未访问 GitHub、WebDAV、HTTP 真实同步端点，未读取或改动用户浏览器存储、令牌、口令。
- 官方平台限制由父任务另行核对。本文不凭记忆给出 Gist 文件限额、限流额度或声称 GitHub 支持条件 PATCH。
- 用户已选择：保留纯本地使用，允许可选自建增量同步服务；保留 Gist/WebDAV v1 兼容，不自动迁移或写入真实远端。

## 结论

现有 Gist/WebDAV/HTTP 是**单文件全量快照传输、记录级合并**。它能承担小体量个人数据同步，但当前实现不能作为持续增长聊天数据的增量同步底座，也没有可靠的跨设备并发提交协议。把聊天从 localStorage 移到 IndexedDB 并不能改变网络传输成本。

建议先统一本地存储并修复 v1 的可确认数据丢失路径，再增加独立、可选的 v2 增量服务。Gist/WebDAV 作为兼容后端保留，清楚展示它们的快照性质与能力边界，不把“上传 1 条”解释成只传了 1 条。

最优先的发现：IDB 错误被视为空数据时会生成删除墓碑；full 同步会覆盖 GET 等待期间产生的新本地修改；新增口令不一定实际加密远端；关闭密钥同步后仍可把已有远端密钥传回；未知同步版本能被误读为空快照并覆写。这些问题应先于扩容优化解决。

## 自动同步现状

`src/lib/sync.ts:515–538` 的触发为：启动 1.5 秒后 full；可见页面每 3 分钟 push；切到后台 full；回前台且距上次超过 1 分钟则 push；联网恢复 push。push 仍拉取、解析、合并整个云端，只是不向本机应用远端记录。

full 拉取后靠刷新页面更新业务内存（`:527`、`:543–544`），同步层直接写 localStorage/IDB，并不通知 `store.ts`、`componentData.ts`、聊天缓存。当前有单模块 `running` Promise 去重，但不是跨标签页锁（`:400–411`）。等待中的 full 请求可能复用先运行的 push，不能保证它真的执行了 full。

没有网络超时/AbortSignal、429/5xx 退避、请求字节统计、文件大小预警或条件 GET。后端错误只会在设置页留下状态；这不是对大体积或不稳定网络的完整调度协议。

## Gist 与条件写入的准确边界

Gist **已有** `truncated && raw_url` 的完整内容读取分支（`sync.ts:339–342`），不能把它记录成“完全不支持大文件读取”。现有不足是 raw 响应状态未校验；`truncated:true` 却缺少 raw_url 时继续使用 content；请求没有超时/体积校验；读取/更新仍只有一个全量文件。平台实际截断条件与文件上限需结合官方来源另行核实。

WebDAV/HTTP 会在 GET 返回可见 ETag 时带 `If-Match` 写回（`sync.ts:318–322,369–373`），412 会整轮重试一次（`:297,502`）。这只能覆盖真正支持并执行条件写的服务器，以及浏览器可读到 ETag 的情况；没有 ETag 就是无条件 PUT，GET 404 后的首次写也没有 `If-None-Match:*`。测试连接只做读取和解密，无法证明写权限、条件写语义或跨域响应头正确。

Gist 不返回本地使用的 ETag，也不在 PATCH 中带条件写；不要仅加一个 header 就宣称修复并发。若官方接口没有受支持的原子条件写，Gist v1 只能明确展示尽力同步的限制。可补写后重读和有限重试以提高发现概率，但这不构成并发无损保证。要保证并发，使用具备原子版本检查的 v2 服务或设计新的版本化日志后端，后者不是 v1 兼容补丁。

当前 full 先 apply 本机，再提交远端；提交失败时没有统一回滚或缓存刷新（`sync.ts:478–505`）。错误后重试也从本机已被改写的状态重新推导时间戳。这条路径应在入站版本保护修复时一起覆盖，不应只给 GET 加重试。

## App/Applet 搬到 IDB 时保持 v1 记录身份

当前 App `tada.store` 写 `fp.app.<instanceId>`（`src/widgets/app.tsx:220–241`）；Applet `persist` 写 `fp.applet.<instanceId>`（`src/widgets/applet.tsx:70,97,105–108`，`src/lib/store.ts:15,31`）。两者已经被现有 `fp.*` 扫描同步，也被备份 localStorage 部分包含。迁移是持久化位置变化，不是“首次纳入同步”。

假设统一存储把它们改放 IDB 内部键 `application-data/...`，必须有兼容投影；具体物理键由存储设计决定，不能让物理键自动成为新同步 ID。

| 层 | 迁移后的约束 |
| --- | --- |
| 存储内部 | App 和 Applet 通过同一仓库读写，业务数据、revision 与 outbox 有一致事务边界；物理键可调整。 |
| v1 导出 | App 仍导出 `ls:fp.app.<id>`；Applet 仍导出 `ls:fp.applet.<id>`；值结构保持兼容。不得再额外导出其内部 `kv:<新键>`。 |
| v1 导入 | 识别以上旧逻辑 ID，交给统一仓库写 IDB，同时更新缓存/订阅；不能继续落到没人读取的 legacy LS。普通设置 `ls:*` 保留各自领域入口。 |
| 本机迁移 | 只有写入并读回校验成功才完成迁移；失败保留源数据。保留逻辑记录 hash 与 t，不能因搬迁制造墓碑或更晚时间。 |
| 同步 meta | 原 `ls:*` meta 接续使用；原值没改，迁移前后 export 输出相同；若既有 LS 又有 IDB，按明确迁移标记/版本决定一次，不能每次猜。 |
| 旧备份 | 导入 legacy LS 应经过迁移入口；导出格式保留兼容投影或明确版本，不把内部 IDB 键泄漏为旧客户端不认识的数据。 |

这样旧版本在**另一台设备**仍收到原来的 `ls:*` 对象，新版本收到旧客户端回写也能进统一仓库。仅靠“IDB 的所有 kv 都会同步”会产生删旧增新，导致旧客户端仍读旧数据或把旧对象重新传回来。

需要单独声明的边界：同一浏览器 origin 同时运行旧代码标签页时，删掉 legacy LS 会让旧代码读空；另一台设备兼容并不能解决此问题。不要用长期双写两个独立真相来掩盖它。实施前应选择迁移协调策略：版本握手/标签页协调后再切换，或有期限且带 revision 的兼容桥。若只承诺跨设备 v1 数据格式兼容，则明确禁止旧标签页继续写并提示更新；单纯静默删除 LS 不满足同 origin 旧版本兼容。

## v2 增量的最小正确性契约

新增 v2 应使用独立端点/格式，不能把 v2 内容写进老客户端会读取的 `dada-sync.json`。当前老 reader 不检查 v，可能覆盖未知版本；命名隔离比只改 v 字段可靠。

核心字段可从 `recordId、localRevision、serverRevision、operationId、deviceId、deleted、payload` 起步，具体名称交由正式 design 确定。服务端分配单调变更游标，客户端记录每个目标的游标和待发送操作，不用本机墙钟决定最终先后。

1. **本地写入**：统一仓库同一 IDB transaction 更新业务值、递增 localRevision，并写 durable outbox。成功前不丢弃旧待发版本；删除也是有版本的操作。
2. **出站提交**：操作有稳定 operationId 与预期 serverRevision。服务端原子比较、提交并去重；重复请求返回同一确认，不重复生效。冲突返回当前远端版本，不能直接覆盖。
3. **确认处理**：服务端确认的是具体 operationId/revision，客户端仅清理被确认的那一版。在请求期间写出的新版本继续留在 outbox。
4. **入站应用**：取数前记录本地 revision。真正 apply 时在同一 IDB readwrite transaction 内重读记录和 outbox；只有本地 revision 没变且没有未确认本地操作，才替换。若已变化，保留本地值与新 outbox，并保存远端基线/冲突供后续合并，不能清掉 pending。
5. **游标提交**：一页远端变更须全部成功应用或持久化到冲突队列，才与这些操作在同一事务推进 cursor。失败/断电后重放必须幂等；拒绝部分写完后误报整页成功。
6. **业务缓存**：成功提交后由仓库通知对应订阅，保持内存和 IDB 一致。不能直接写数据库后期待下一次刷新；也不能全局 `dropPendingData()`。
7. **墓碑与过期**：按客户端确认水位或明确过期策略回收。落后于历史保留窗口的客户端必须获取完整基线，并保留/核对自己的未上传修改；不能把远端缺失当成恢复旧值授权。
8. **大数据**：变更按有界页读取；聊天轮次独立记录。一次初始同步可分批，随后一条新轮次只传对应增量和必要会话元数据。整个应用业务对象仍可能很大，行级同步需另立业务模型，不伪称已有。

若工作空间/设置仍以 localStorage 为唯一写入真相，就无法与 IDB 的 outbox/cursor 形成同一事务。需在 design 明确这些同步记录也通过 IDB 的持久化事务进入同步，或设计可恢复的日志桥。不能只对 App 数据做事务，然后宣称所有同步记录都有原子保障。

未启用同步时不发送同步请求，也不需要同步账户；AI、RSS、天气等网络功能仍按各自配置工作。打开 v2 不自动改动已有 v1 端点；初次导入现有 v1 快照是用户选择的迁移步骤，必须保留备份和失败恢复证据。
